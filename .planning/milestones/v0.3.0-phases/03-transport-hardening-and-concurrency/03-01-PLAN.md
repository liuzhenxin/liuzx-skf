# Plan 03-01: Bounded Frames, Payloads, and Connections

<objective>
让服务在超大帧、超大操作载荷和过量并发连接下保持有界：帧与消息在 tungstenite 分配前被拒；base64 载荷在 decode 前按编码长度预检；并发连接数有 64 的上界且超限连接被明确拒绝。

这是 TRANS-01 / TRANS-02 的实现，依据 03-CONTEXT D-12（1 MiB 帧）、D-13（256 KiB 载荷、decode 前校验）、D-14（64 连接、`try_acquire` 拒绝）。
</objective>

<threat_model>
**ASVS Level:** 1 · **Block on:** high

| ID | Threat | Severity | Mitigation in this plan |
|----|--------|----------|-------------------------|
| T-03-01 | 超大帧导致 tungstenite/服务在解析前分配巨量内存 → OOM/拒绝服务 | HIGH | `WebSocketConfig{max_message_size,max_frame_size}` 在帧读取阶段拒绝 |
| T-03-02 | 超大 base64 参数在 decode 时分配超限内存 | HIGH | 编码长度预检（`encoded.len() <= 256KiB*4/3+4`），**先于** `base64::decode` |
| T-03-03 | 连接风暴耗尽文件描述符/任务 | MEDIUM | `Semaphore(64)` + `try_acquire`，超限立即丢弃并记日志 |
| T-03-04 | 新增错误码/消息扰动冻结契约 | MEDIUM | 复用 `-2`，仅超限路径新增消息；`contract_fixtures` 必须保持 37/37 |
</threat_model>

<must_haves>
- `spawn_client` 使用 `accept_async_with_config`，`max_message_size = Some(1 MiB)`、`max_frame_size = Some(1 MiB)`
- `Params` 提供带 256 KiB 预检的 base64 decode 辅助，所有迁移分支的 payload decode 走该辅助
- `serve` 持有 `Semaphore(64)`，第 65 个并发连接的握手失败并记录日志
- `cargo test --test contract_fixtures` 37/37
- 新测试 `tests/transport_limits.rs` 覆盖超限帧、超限载荷、连接上限
</must_haves>

<task id="03-01-02" type="execute">
  <name>base64 载荷 256 KiB 预检辅助并接入迁移分支</name>
  <files>src/protocol/params.rs, src/domain/container.rs, src/domain/crypto.rs</files>
  <read_first>
    - `src/protocol/params.rs` 全文（现有 `required_base64` / `optional_base64` / `reject` 与其 12 条测试）
    - `src/domain/crypto.rs` 中全部 `STANDARD.decode(` 调用点（SignData、RSASignData、EncryptData、DecryptData、CreatePKCS10）
    - `src/domain/container.rs` 中 `decode_certificate` 与 `cert_str` 处理
    - `.planning/phases/03-transport-hardening-and-concurrency/03-CONTEXT.md` — D-13
  </read_first>
  <action>
    1. 在 `src/protocol/params.rs` 新增：
       ```rust
       /// Decoded-payload ceiling. The encoded form is checked before decoding.
       pub const MAX_PAYLOAD_BYTES: usize = 256 * 1024;
       ```
       并在 `impl<'a> Params<'a>` 增加：
       ```rust
       /// Decode a base64 string, rejecting an over-limit payload before allocation.
       ///
       /// The encoded length is checked first: `max_encoded = MAX_PAYLOAD_BYTES * 4 / 3 + 4`.
       /// On success the message shape matches the pre-refactor
       /// `format!("{message}: {error}")`; on over-limit it returns `-2` with
       /// `"Payload too large: {len} bytes (limit {MAX_PAYLOAD_BYTES})"`.
       pub fn decode_base64(
           &self,
           encoded: &str,
           message: &str,
       ) -> Result<Vec<u8>, RpcResponse>
       ```
       实现顺序必须是：先 `if encoded.len() > MAX_PAYLOAD_BYTES * 4 / 3 + 4 { return Err(self.reject(&format!("Payload too large: {} bytes (limit {})", encoded.len(), MAX_PAYLOAD_BYTES))); }`，再 `base64::engine::general_purpose::STANDARD.decode(encoded).map_err(|e| self.reject(&format!("{}: {}", message, e)))`。
    2. 在 `src/domain/crypto.rs` 把每个 payload decode 的 `match base64::engine::general_purpose::STANDARD.decode(X) { Ok(b)=>b, Err(e)=> return RpcResponse::err(-2, format!("{msg}: {e}"), id) }` 改为 `match params.decode_base64(X, "{msg}") { Ok(b)=>b, Err(e)=> return e }`，其中 `{msg}` 保持原文本逐字：`"Invalid base64 data"`、`"Invalid base64 IV"`、`"Invalid base64 symKey"`、`"Invalid base64 encrypted data"`。**不要**改动 `required_str` 的存在性检查与其 `"Missing ... param"` 消息。
    3. 在 `src/domain/container.rs` 的 `decode_certificate` 路径：`ImportCertificate` 对非 PEM 的 `cert_str` 使用 `params.decode_base64(cert_str, "Invalid cert base64")`；PEM 分支的剥离后 decode 保持现有"失败回退原始字节"语义不变（这是契约行为），但其输入 `cert_str` 同样先经过 `params.decode_base64` 的长度预检——实现方式：在进入 `decode_certificate` 之前，若 `cert_str.len()` 超限则返回 `params.decode_base64(cert_str, "Invalid cert base64")` 的错误。保持 `-3 Invalid cert base64: {e}` 的既有形状用于非 PEM decode 失败。
    4. 在 `params.rs` 的 `#[cfg(test)] mod tests` 增加：
       - `payload_at_the_exact_limit_is_accepted`：构造 `MAX_PAYLOAD_BYTES` 可解码字节（如全零）的 base64，断言 `Ok` 且长度正确；
       - `payload_over_the_limit_is_rejected_before_decode`：构造 `MAX_PAYLOAD_BYTES + 1` 的编码串，断言 `error == -2` 且 `message` 含 `"Payload too large"`；
       - 断言超限消息不含 `"base64"`（证明未走到 decode）。
  </action>
  <acceptance_criteria>
    - `grep -c 'MAX_PAYLOAD_BYTES' src/protocol/params.rs` 输出 `>= 3`
    - `grep -c 'pub fn decode_base64' src/protocol/params.rs` 输出 `1`

  <files>src/server/mod.rs</files>
  <read_first>
    - `src/server/mod.rs` 的 `serve`（两个 `listener.accept()` 分支）与 `spawn_client`
    - `.planning/phases/03-transport-hardening-and-concurrency/03-CONTEXT.md` — D-14
  </read_first>
  <action>
    1. 在 `src/server/mod.rs` 顶部新增常量 `const MAX_CONNECTIONS: usize = 64;`。
    2. 在 `serve` 中创建 `let permits = Arc::new(tokio::sync::Semaphore::new(MAX_CONNECTIONS));`，并在两个 accept 分支里对每个 `(stream, peer)`：
       - 用 `Arc::clone(&permits).try_acquire_owned()` 获取许可；
       - `Ok(permit)` → 把 `permit` 传给 `spawn_client`（新增参数，持有到连接结束，随连接任务 drop 释放）；
       - `Err(_)` → `log::warn!("connection limit {} reached; refusing {:?}", MAX_CONNECTIONS, peer)` 并 `drop(stream)`，不握手。
       - 注意 `peer` 来自 accept 的 `Ok((stream, peer_addr))`，当前代码用 `Ok((stream, _))`，改为绑定 `peer`。
    3. `spawn_client` 签名改为 `fn spawn_client<S>(sessions: Arc<S>, stream: TcpStream, _permit: tokio::sync::OwnedSemaphorePermit)`，在函数体开头 `let _keep = _permit;`，确保许可存活到连接任务结束。
    4. 不改动 `bind`、`run_server`、`Session` 接缝。
  </action>
